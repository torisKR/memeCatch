## 2. 확인한 근거

### 2.1 프로덕션 재현 (읽기 전용 GET)

```
$ curl -sI https://catchmeme.com/memes/zzzzzzzz
HTTP/2 200
age: 2132
content-length: 55187
etag: "rvqsq1iual15e7"
vary: rsc, next-router-state-tree, next-router-prefetch, next-router-segment-prefetch
x-matched-path: /memes/[key]
x-nextjs-prerender: 1
x-nextjs-stale-time: 300
x-vercel-cache: STALE
```

응답 HTML(53,607자) 분석:

| 항목 | 값 |
| --- | --- |
| `<title>` | `밈을 찾을 수 없어요 \| 밈캐치` |
| `<meta name="robots" content="noindex"/>` 위치 | **byte 4743** |
| `</head>` 위치 | byte 4839 |
| → 판정 | **noindex가 `<head>` 안에 있다** (Google이 요구하는 위치) |

대조군:

| URL | 상태 | `x-matched-path` | noindex |
| --- | ---: | --- | ---: |
| `/qqqq` (라우터 미매치) | **404** | `/404` | 1 |
| `/memes/uefmryky` (정상) | 200 | `/memes/[key]` | 0 |
| `/memes/zzzzzzzz` | **200** | `/memes/[key]` | 1 |
| `/en/memes/zzzzzzzz` | **200** | `/[locale]/memes/[key]` | 1 |

→ `[locale]` 변형도 **같은 결함을 가진다**(루프 019에서 미확인이던 부분).

봇 User-Agent 3종(Googlebot / bingbot / facebookexternalhit)으로 같은 URL 요청:

```
Googlebot            -> HTTP/2 200  x-nextjs-prerender: 1  x-vercel-cache: HIT
facebookexternalhit  -> HTTP/2 200  x-nextjs-prerender: 1  x-vercel-cache: HIT
bingbot              -> HTTP/2 200  x-nextjs-prerender: 1  x-vercel-cache: HIT
```

→ Next의 "HTML-limited 봇에는 metadata를 블로킹한다"는 탈출구는 **여기서 작동하지 않는다**.
`vary` 헤더에 `user-agent`가 없어 ISR 캐시가 UA를 구분하지 않고, 먼저 채워진 200이 모두에게 그대로 나간다.

Next dist 코드에서 noindex 주입 지점 확인 —
`node_modules/next/dist/server/app-render/make-get-server-inserted-html.js:44-51`:

```js
if (isHTTPAccessFallbackError(error)) {
    errorMetaTags.push(jsx("meta", { name: "robots", content: "noindex" }, error.digest), ...
```

### 2.2 Next 16.2.10 공식 문서 — 이것은 버그가 아니라 문서화된 동작

`node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/not-found.md:13`

> Next.js will return a `200` HTTP status code for streamed responses, and `404` for non-streamed responses

`.../03-file-conventions/loading.md` → **Status Codes** 절 (원문 요지, 인용은 최소로)

- 스트리밍이 시작되면 헤더가 이미 나갔으므로 **상태 코드를 바꿀 수 없다**.
- 404를 스트리밍할 때 Next는 HTML에 `noindex`를 넣고, 문서는 이 경우 색인으로 이어지지 않는다고 본다.
- 일부 크롤러가 이를 "soft 404"로 라벨링할 수 있다고 **명시**한다.
- 진짜 404 상태가 필요하면 **본문 스트리밍 전에** 리소스 존재를 확인하라고 안내하고,
  그 위치로 **`proxy`** 를 지목한다("Keep proxy checks fast, and avoid fetching full content there").
- 접힌 절 "When is the response body streamed?"이 결정적이다:
  > The response body starts streaming when a Suspense fallback renders (for example, a `loading.tsx`) …
  > Place `notFound()` before those boundaries and before any `await` that may suspend.

→ **`loading.tsx`가 원인으로 문서에 이름까지 적혀 있다.** 이 저장소에는
`app/(default)/memes/[key]/loading.tsx` 와 그 조상 `app/(default)/loading.tsx` 가 둘 다 있다.

### 2.4 최소 재현 실험 — 원인 격리

`node_modules`만 심볼릭 링크한 별도 스크래치 앱(저장소 소스 미수정, `next build --webpack` + `next start`).
공통 조건: `experimental.globalNotFound: true`, 다중 root layout, `generateMetadata`와 페이지 본문 양쪽에서 `notFound()`.

실험 페이지 (전 라우트 동일 코드):

```tsx
// app/(group)/itemsN/[key]/page.tsx
import { notFound } from "next/navigation";
export const revalidate = 600;                       // (items5·6만 dynamic = "force-dynamic")
export async function generateStaticParams() { return []; }
async function load(key: string) {
  await new Promise((r) => setTimeout(r, 20));       // 서스펜드 유발
  return key === "ok" ? { title: "OK ITEM" } : null;
}
export async function generateMetadata({ params }) {
  const { key } = await params; const item = await load(key);
  if (!item) notFound();
  return { title: item.title };
}
export default async function Page({ params }) {
  const { key } = await params; const item = await load(key);
  if (!item) notFound();
  return <p>ITEM {item.title}</p>;
}
```

읽는 법:

1. **유일한 결정 변수는 세그먼트 체인 위의 `loading.tsx`다.** ISR인지 force-dynamic인지는 무관하다.
2. `loading.tsx`가 **조상 그룹 루트**(`app/(default)/loading.tsx` 위치)에 있어도 동일하게 200이 된다 →
   `app/(default)/memes/[key]/loading.tsx` **하나만 지워서는 해결되지 않는다**.
3. `root-document.tsx`의 `<Suspense fallback={null}><NavProgress/></Suspense>`(client + `useSearchParams`)는
   **범인이 아니다** — 그것만 있고 `loading.tsx`가 없으면 404가 정상적으로 나온다(`/items3` 1행).
4. 404가 나오는 경우에도 ISR은 유지된다: `/items2/ok`·`/items3/ok` 모두
   `x-nextjs-prerender: 1`, `Cache-Control: s-maxage=600, stale-while-revalidate=31535400`.

### 3.1 기각된 가설 — `htmlLimitedBots: /.*/`

"스트리밍 metadata를 끄면 `generateMetadata`의 `notFound()`가 스트림 전에 확정된다"는 가설을 별도 빌드로 검증했다.

```ts
// next.config.ts (실험)
const nextConfig: NextConfig = {
  experimental: { globalNotFound: true },
  htmlLimitedBots: /.*/,          // 스트리밍 metadata 전면 비활성
};
```

결과: `/items/missing` **200**, `/items3/missing` **200**, `/deep/items4/missing` **200** — **효과 없음**.
`loading.tsx`의 Suspense fallback이 metadata와 무관하게 스트림을 먼저 연다. 다음 루프에서 재시도할 필요 없다.

## 4. 선택지별 구현안과 영향

### 4.1 D 유지 — 지금 당장 해야 하는 것 (코드 변경 0)

D는 "아무것도 안 함"이 아니라 **"noindex에 기대는 것"** 이다. 그 전제가 계속 참인지 감시해야 한다.

| 항목 | 현재 값 | 감시 방법 |
| --- | --- | --- |
| noindex가 `<head>`에 있음 | 확인됨 (byte 4743 < 4839) | 아래 smoke 확장 |
| robots.txt가 `/memes/`를 막지 않음 | 확인됨 (`app/robots.ts`의 `DISALLOWED_PATHS`에 없음) | 변경 시 재확인 |
| sitemap에 미존재 URL 없음 | 구조상 DB에서 생성 | — |
| **ISR 캐시 오염** | 가짜 키 1건당 **55,187 byte + 약 1.03 s 함수 시간** | 미관측 — §4.1.1 |

`scripts/smoke.mts`는 이미 이 URL을 `knownIssue: "SEO-001"`로 감시한다.
D를 "의도된 상태"로 확정한다면 기대값을 **404가 아니라 "200 + head 안 noindex"** 로 바꿔야 한다.
그래야 noindex가 사라지는 회귀를 잡는다. 문서 안 제안 diff:

```diff
--- a/scripts/smoke.mts
+++ b/scripts/smoke.mts
@@
-  // 존재하지 않는 문서 → 404이어야 하나, 현재 not-found UI가 200 + ISR 캐시로
-  // 나간다(soft-404). generateMetadata에 notFound()를 넣어도 재현 — Next 16 ISR
-  // 경로의 더 깊은 문제로 SEO-001에 기록. 고쳐지면 knownIssue를 지워 승격한다.
-  { path: "/memes/zzzzzzzz", markers: [], knownIssue: "SEO-001" },
+  // 존재하지 않는 문서. Next 16의 스트리밍 응답은 200을 되돌린다(문서화된 동작,
+  // loading.md#status-codes). 색인 방어선은 상태 코드가 아니라 <head>의 noindex다 —
+  // HG-007에서 D안을 유지하는 근거이므로 그 방어선 자체를 게이트로 감시한다.
+  // 진짜 404로 승격되면(HG-007 E·C안) 이 항목을 markers: [] 기대값으로 되돌린다.
+  {
+    path: "/memes/zzzzzzzz",
+    markers: ['<meta name="robots" content="noindex"/>'],
+    knownIssue: "SEO-001",
+  },
```

> 주의: 위 marker는 `</head>` **이전**에 있어야 의미가 있다. smoke는 문자열 포함만 보므로
> 위치 검증까지 넣으려면 `body.indexOf(marker) < body.indexOf("</head>")` 비교가 추가로 필요하다.
> 지금 그 한 줄을 넣을지는 코드 변경이 허용되는 루프에서 결정한다.

#### 4.1.1 ISR 캐시 오염 — 실측 비용

가짜 키 3개(`qw3rt9zx`, `pl0okm9n`, `zx8cv7bn`)를 프로덕션에 처음 요청한 결과:

| 키 | TTFB | 크기 | 캐시 |
| --- | ---: | ---: | --- |
| qw3rt9zx | 1.016 s | 55,187 B | MISS → prerender 저장 |
| pl0okm9n | 1.048 s | 55,187 B | MISS → prerender 저장 |
| zx8cv7bn | 1.049 s | 55,187 B | MISS → prerender 저장 |

임의의 URL마다 **약 1.03 s의 서버리스 렌더 + 55 KB의 ISR 엔트리**가 새로 생긴다. 상한이 없다.
스캐너·깨진 백링크가 이 경로를 두드리면 캐시 용량과 함수 호출이 선형으로 늘어난다.
**D의 실제 비용은 SEO가 아니라 이것이다.** DECISIONS.md의 D 서술("색인 오염 위험 지속")은 정정이 필요하다.

### 4.3 A(`force-dynamic`) — 정확한 성능 영향 추정

**결론부터: A는 채택 불가다. 결함을 고치지 못하면서(§3 `/items5`) 비용만 낸다.**
그럼에도 요청된 수치를 남긴다 — 향후 다른 라우트의 `force-dynamic` 논의에 재사용 가능하다.

#### 측정 방법

1회차 = 콜드(MISS, 실제 SSR + DB), 2회차 = 웜(HIT, CDN). 데스크톱 Chrome UA, 서울에서 측정.

#### 영향 추정

| 지표 | 현재 (ISR 600) | A 적용 시 | 변화 |
| --- | ---: | ---: | ---: |
| 상세 TTFB (중앙값) | **0.129 s** | **2.019 s** | **+1.890 s / ×15.6** |
| LCP (기준선 로컬 프로덕션 빌드) | 1,131 ms | ≈ 3,021 ms (추정) | Core Web Vitals "좋음" 임계 **2,500 ms 초과** |
| 문서당 렌더 상한 | 600초당 1회 = **≤144회/일** | **요청 1건당 1회** | 요청량에 선형 |
| 요청당 Vercel 함수 호출 | 캐시 HIT은 **0회** | **매 요청 1회** | — |
| 렌더 1회당 PostgREST 왕복 | **8회** (아래) | 동일, 다만 요청마다 | 요청량에 선형 |

> LCP 추정의 가정: 기준선 LCP 1,131 ms는 `BASELINE.json`의 **로컬 프로덕션 빌드** 측정치이고,
> TTFB 두 값은 프로덕션 네트워크 측정치다. 두 환경이 달라 엄밀한 합산은 아니다.
> "TTFB 증가분 +1.89 s가 LCP에 그대로 더해진다"는 보수적 가정하의 추정이며, 하드 수치는 TTFB 쪽이다.

#### 렌더 1회의 DB 왕복 8회 (코드 기준 실측 아님, 호출 경로 계수)

| 순서 | 호출 | PostgREST 요청 수 | 근거 |

| 2 | `getAvailableTranslationLocales` | 2 | `lib/meme-translations.ts:280` — memes + meme_translations 병렬 |
| 3 | `getLocalizedMemeByShortId` × N | **0** | 프로덕션 `meme_translations` 중 `status=reviewed` **0건** (PostgREST `content-range: */0`) |

### 4.4 C(proxy 선제 404) — Next 공식 권장안

문서가 지목한 위치다. 다만 이 저장소의 `proxy.ts:57`은 지금 `/my`·`/premium`·`/submit`·`/admin`·`/login`
에서만 Supabase를 호출하고 나머지는 즉시 통과시킨다. 여기에 `/memes/*` 존재 확인을 넣으면
**ISR 캐시 HIT 경로에도 조회가 붙는다**(proxy는 캐시 앞에서 실행된다).

- 비용: 상세 요청 전건에 왕복 1회 추가. 현재 웜 TTFB가 0.129 s이므로 30–80 ms만 붙어도 **+25~60 %**.
- 문서 경고("Keep proxy checks fast, and avoid fetching full content there")를 지키려면 DB 조회 자체를 피해야 한다.
- **DB 없는 변형**: 3,904개 short_id(8자)를 블룸 필터로 만들면 오탐률 1 %에서 약 4.7 KB.
  proxy 번들에 인라인하면 왕복 0회로 "확실히 없음"만 404 처리할 수 있다.
  **위험**: 필터 생성 이후 새로 published된 밈은 필터에 없어 **정상 문서가 404**가 된다.
  발행 시점에 필터를 갱신하는 경로가 없으면 채택 불가다.
- 마이그레이션 SQL: **불필요**. C는 스키마를 건드리지 않는다(HG-007 전 선택지가 그렇다).

### 4.5 E(신규) — `loading.tsx` 제거. ISR을 지키는 유일한 코드 수정

§3이 증명한 대로, 세그먼트 체인에서 `loading.tsx`를 없애면 **ISR을 유지한 채** 진짜 404가 나온다.
`/memes/[key]` 체인에 걸린 파일은 두 개다.

```
app/(default)/loading.tsx              ← 조상. 이것만 남아도 200이 된다(/deep/items4 결과)
app/(default)/memes/[key]/loading.tsx  ← 세그먼트
```

`[locale]` 쪽도 동일하다:

```
app/[locale]/loading.tsx               ← 조상 (app/[locale]/memes/[key]에는 자체 loading.tsx 없음)
```

#### E-1: 두 파일 삭제 (최소 diff, 최대 부수효과)

```diff
--- a/app/(default)/memes/[key]/loading.tsx
+++ /dev/null
@@ -1,5 +0,0 @@
-import { MemeDetailSkeleton } from "@/components/skeletons";
-
-export default function MemeDetailLoading() {
-  return <MemeDetailSkeleton />;
-}
```

```diff
--- a/app/(default)/loading.tsx
+++ /dev/null
```

- 얻는 것: `/memes/zzzzzzzz` → **404**, ISR(`revalidate = 600`) 유지, `force-dynamic` 불필요, DB 부하 불변.
- 잃는 것: **`(default)` 트리 전체**(`/`·`/explore`·`/rankings`·`/search`… 20여 개 route)의 즉시 로딩 상태.
  클라이언트 내비게이션 시 이전 화면이 그대로 멈춰 있게 된다.
- 회귀 위험: `BASELINE.json`의 상세 CLS **0.12(콜드)/0.00(웜)**, LCP 1,131 ms가 다시 흔들릴 수 있다.
  게이트 D의 CLS 항목이 이미 미달이라 **재측정 없이 적용하면 안 된다**.
- 부가 위험: `RELEASE_CHECKLIST` 게이트 D에 "SSR HTML에 영구 로딩 문구가 없다" 항목이 있고,
  루프 016에서 그 문구가 `loading.tsx`의 `sr-only` 알림임이 확인됐다. 삭제 시 이 접근성 알림도 사라진다.

#### E-2: `/memes/[key]`만 별도 root layout 그룹으로 분리 (범위 최소화, 비용 큼)

`app/(doc)/memes/[key]/…` + `app/(doc)/layout.tsx`(자체 root layout, `loading.tsx` 없음)로 옮기면
나머지 `(default)` route의 `loading.tsx`를 지키면서 상세만 404를 얻는다.

**하지만 Next 문서가 명시적으로 경고한다** —
`node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/route-groups.md:30`:

> **Full page load**: If you navigate between routes that use different root layouts, it'll trigger a full page reload.

즉 `/explore`에서 밈 카드를 눌러 상세로 가는 **핵심 동선이 전부 전체 페이지 리로드**가 된다.
`loading.tsx`를 지키려다 그보다 큰 내비게이션 비용을 내는 교환이라 **권장하지 않는다**.

   D의 실제 비용은 색인이 아니라 **무제한 ISR 캐시 오염(가짜 URL당 55 KB + 1.03 s)** 이다.

   C는 범위가 좁지만 요청 전건에 지연 또는 갱신 경로가 필요한 블룸 필터를 요구한다.
