## 2. 판정 규칙 — 「4칸 동일값이면 미확인인가?」에 대한 답

### 2.1 결론: **아니다. 「4칸 전부 `green`」일 때만 미확인으로 표시한다.**

학교폭력·섭식장애·차별 용어다. 「어디서도 쓰지 마세요」는 **동일값인 것이 정상인 판정**이다. 여기에 「상황별 판정 미확인」을 붙이면 확인된 경고를 미확인으로 낮추게 된다.

**비대칭 위험 원칙:** 균일한 **관대**(전부 `green`)는 갖지 않은 확인을 주장하므로 사용자가 손해를 본다. 균일한 **엄격**(전부 `red`/`yellow`/`gray`)은 보수적이라 4행에 같은 경고를 반복해도 비용이 없다. 그래서 규칙은 의도적으로 한쪽만 본다.

### 2.2 규칙 정의

```
isUnverified(rows) := rows.length >= 2 && rows.every(r => r.level === "green")
```

문서 등급(`safety_level`)은 보지 않는다 — `uniform_contradiction` 9건(`gray`7·`yellow`2)도 이 규칙에 걸려 초록 표가 숨겨진다. 그게 정확히 원하는 동작이다.

`rows.length >= 2`는 `scripts/quality-check.mts:141` `isUniformUsageContext()`의 하한과 맞춘 것이다. 실측상 유효 칸이 1~3개인 문서는 0건이라 하한 선택이 결과를 바꾸지 않는다.

## 5. 데이터 재판정 우선순위 — `red`·`gray` 271건

`safety_level in ('red','gray')` = `red` 103 + `gray` 168 = **271건**.

### 5.1 추출 쿼리 (읽기 전용 — 재현용)

```sql
-- P0: red 문서에 green 칸이 있는 문서
select short_id, title, safety_level, usage_context, caution
from public.memes
where moderation_status in ('approved','limited')
  and safety_level = 'red'
  and (usage_context->>'work' = 'green'
    or usage_context->>'friends' = 'green'
    or usage_context->>'family' = 'green'
    or usage_context->>'sns' = 'green')
order by title;

-- P1: gray 문서인데 직장·가족이 green
select short_id, title, usage_context
from public.memes
where moderation_status in ('approved','limited')
  and safety_level = 'gray'
  and (usage_context->>'work' = 'green' or usage_context->>'family' = 'green')
order by title;

-- P2: 4칸 동일값이면서 green이 아님
select short_id, title, safety_level, usage_context
from public.memes
where moderation_status in ('approved','limited')
  and safety_level in ('red','gray')
  and usage_context->>'work' <> 'green'
  and usage_context->>'work' = usage_context->>'friends'
  and usage_context->>'work' = usage_context->>'family'
  and usage_context->>'work' = usage_context->>'sns'
order by safety_level, title;
```

## 6. 마이그레이션 SQL — **1단계에는 필요 없다**

§3은 데이터를 쓰지 않는다. 아래 SQL은 **첫 재판정이 끝나 「확인했고 실제로 전부 `green`이다」를 표현해야 할 때**만 필요하다. 그 전에 적용하면 값이 전부 `null`인 컬럼이 하나 늘 뿐이다(YAGNI).

```sql
-- 2단계에서만. 지금 적용하지 말 것.
alter table public.memes
  add column usage_context_reviewed_at timestamptz;

comment on column public.memes.usage_context_reviewed_at is
  '상황별 사용 신호를 사람이 상황별로 나눠 확인한 시각. '
  'null이면 상세에서 4칸 전부 green인 문서를 「상황별 판정 미확인」으로 표시한다.';

-- 롤백
alter table public.memes drop column usage_context_reviewed_at;
```

2단계 규칙: `isUnverified = (4칸 전부 green) && usage_context_reviewed_at is null`.

**`usage_context` jsonb에 5번째 키를 넣는 방식은 쓰지 말 것.** `parseUsageContext()`는 모르는 키를 무시하므로 읽기는 되지만, `lib/actions/admin.ts:211`·`:370`이 `usage_context: input.usageContext`로 객체 전체를 덮어쓴다 — 운영자가 저장하는 순간 마커가 조용히 사라진다.

## 7. 사람이 결정해야 하는 것 (이 문서가 답하지 않은 것)

1. **`red` 문서 84건의 `friends: green`을 어떻게 할 것인가.** 「비하·혐오 밈이라도 친구끼리는 통한다」를 서비스가 안내할지는 편집 원칙 결정이다. §3의 표시 변경으로는 하나도 바뀌지 않는다.
2. **미확인 안내문의 최종 문구.** §3.2는 초안이다.
3. **HG-002와 묶을 것인가.** `gray` 168건이 P1·P3에 그대로 겹친다. `DECISIONS.md` HG-002 추천안이 「HG-003과 함께 한 번에」이므로, `gray`를 안전 축에서 빼는 결정이 먼저 나오면 P1 15건의 판정 기준 자체가 바뀐다.
4. **`meme_revisions` 스냅샷이 실제로 기록되는지**(§4.5). 데이터 재판정의 유일한 롤백 경로다.
