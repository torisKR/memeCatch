# HG-001 구현안 — 충실도 임계값 C안 (색인만 완화, 배너·광고 유지)

- 대상 결정: `docs/renewal/DECISIONS.md` § HG-001, 추천안 **C**
- 측정 시각: 2026-08-04, 프로덕션 **읽기 전용**(PostgREST GET, anon 키)
- 측정 대상: `memes` 중 `moderation_status in (approved, limited)` = **3,904건**
- 소스 코드 변경 없음. 아래 diff는 전부 **초안**이며 이 문서 안에만 존재한다.

## 0. 먼저 알아야 할 것 — 병목은 산문 하한이 아니다

HG-001은 "산문 하한 250자가 높아서 3.7%만 색인된다"는 전제로 쓰여 있다.
분포를 다시 재면 **그 전제가 절반만 맞다.**

`isSubstantial = proseChars >= 250 AND score >= 5` 는 AND 조건인데,
공개 3,904건 중 **`score >= 5`를 만족하는 문서가 애초에 418건(10.7%)뿐이다.**

| 산문 하한을 이렇게 낮추면 | 색인 문서 수 |
| --- | --- |
| 250 (현행) | 145 |
| 200 | 321 |
| 180 | 402 |
| 150 | 415 |
| **0 (산문 관문 완전 제거)** | **418** ← 점수 관문이 만드는 절대 상한 |

즉 **C안을 "산문 하한만" 낮추는 것으로 해석하면 최대 418건(10.7%)에서 멈춘다.**
"96.3%가 색인 밖"이 "89.3%가 색인 밖"으로 바뀔 뿐이다. 이 사실을 모른 채
`MIN_PROSE_CHARS: 150`을 적용하면 "임계값을 100자나 낮췄는데 왜 415건뿐인가"를
배포 뒤에 알게 된다.

**따라서 이 구현안은 두 층으로 나눠 제안한다.**
- **1단계(이번 루프, 되돌리기 쉬움)**: 색인 산문 하한 250 → **180**. 145 → **402건**.
  점수 하한 5점은 그대로 둔다 → 얇은 문서의 성격이 크게 바뀌지 않는다(§4 검증).
- **2단계(별도 결정 필요)**: 점수 하한 5 → 4로 낮출지. 색인 805건까지 늘지만
  "출처 0건" 6건·"렌더 가능한 미디어 0건" 49건이 색인에 들어온다. **이번에는 하지 않는다.**

## 1. 현행 구조 — 하나의 판정이 네 곳을 동시에 지배한다

`lib/content-depth.ts`의 `isSubstantial` 하나가 아래 네 화면 결정을 전부 담당한다.
C안은 이 중 **색인 두 곳만** 떼어내는 작업이다.

| # | 소비처 | 코드 | 지금 쓰는 판정 | C안 적용 후 |
| --- | --- | --- | --- | --- |
| 1 | 사이트맵 등재 | `app/sitemap.ts:208` | `isIndexableMeme` | **완화(180)** |
| 2 | robots noindex | `app/(default)/memes/[key]/page.tsx:106` | `isIndexableMeme` | **완화(180)** |
| 3 | 번역 페이지 공개 | `lib/meme-translations.ts:208` | `isIndexableMeme` | 완화(180) — 실효 없음, §5-4 |
| 4 | 광고 로더 렌더 | `app/(default)/memes/[key]/page.tsx:187` | `isIndexableMeme` | **현행 유지(250)** ← 함수 교체 필요 |
| 5 | 「아직 정리 중」 배너 | `components/doc-status-note.tsx:22` | `contentDepth().isThin` | 현행 유지(250) — 무변경 |
| 6 | 품질 리포트 DQ-H1 | `scripts/quality-check.mts:224` | `contentDepth().isThin` | 문구 정정 필요 |

핵심: **4번이 3번과 같은 함수를 쓰고 있다.** 그래서 `isIndexableMeme`만 낮추면
광고 기준이 같이 낮아진다 — C안의 전제("광고 기준 유지")가 코드에서 깨진다.
4번을 별도 술어로 떼는 것이 이 구현안의 실질적 작업이다.

2점 구간(250자)도 사실상 비어 있다(2건). 정의 배점 3점 중 실제로는 최대 1점만 걷힌다.

> DECISIONS.md의 "최상위 문서조차 `description`이 127자 수준"은 실측과 다르다.
> 정확히는 **중앙값 129자 / p90 173자 / p99 219자 / 최대 254자**다.
> 127자는 최상위가 아니라 중앙값 근처 값이다.

**태그 1점은 구조적으로 획득 불가능하다.** 프로덕션에서 확인:

```
GET /rest/v1/tags?select=*          Range: 0-0  Prefer: count=exact
  → content-range: */0
GET /rest/v1/meme_tags_map?select=*  Range: 0-0  Prefer: count=exact
  → content-range: */0
```

`tags` 테이블 0행, `meme_tags_map` 0행. RLS는 `tags_map_public_read ... using (true)`
(`supabase/migrations/20260708004500_schema_v2.sql:531`)라 **가림이 아니라 실제로 빈
테이블**이다. `DATA_QUALITY_REPORT.json`의 `DQ-M2-no-tags = 3904 (ratio 1)`과 일치한다.
따라서 현 데이터의 **실효 만점은 13점이 아니라 11점**이고, 정의 상한까지 반영하면 10점이다.
`MIN_SCORE: 5`는 실효 10점 만점의 절반이다 — 문서에 적힌 "13점 만점의 5점"보다 훨씬 빡빡한 기준.

### 3-6. 마이그레이션 SQL — **불필요**

C안은 임계값 상수 변경이므로 스키마·데이터 변경이 없다. 확인한 근거:

- 색인·광고·배너 판정은 전부 애플리케이션 계층(`lib/content-depth.ts`)에 있고
  DB에 대응 함수가 없다. `grep -rn "content_depth\|is_substantial" supabase/migrations/` → 0건.
- DB 쪽 게이트인 `is_meme_rank_eligible()` / `meme_ranking_completeness()`
  (`supabase/migrations/20260715003000_content_quality_ranking.sql`)는 **랭킹 진입**만
  통제하고 색인·광고와 무관하다. 이 함수는 태그를 필수 조건이 아닌 5점 가산으로만
  쓰므로(같은 파일 43–46행), 태그 0건 상태에서도 랭킹은 막히지 않는다.
- 사이트맵은 빌드/요청 시 `app/sitemap.ts`가 생성한다. 재생성은 배포로 충분하고
  DB 마이그레이션이 필요 없다.

**따라서 이 구현안에는 SQL이 없다.** (태그 데이터 0건 문제는 별건 — §6 참조.)

## 6. 이 결정이 드러낸 별건 (이번 루프 범위 밖)

1. **태그 데이터가 0건이다.** `tags` 0행, `meme_tags_map` 0행(§2-3). 충실도 배점 1점이
   구조적으로 사장돼 있고, 관련 밈·탐색 품질도 같이 죽어 있다. `DQ-M2` = 100%.
   모든 문서에 태그 3개를 채우면 3,904건 전부가 +1점을 받아 **점수 4점 문서 652건이
   5점이 된다.** 그때 색인은(산문 180 기준) 402 → **805건(20.6%)**으로 두 배가 된다
   — §2-4 매트릭스의 `산문 180 · 점수 ≥4` 칸이 곧 그 값이다. 현행 산문 하한 250을
   유지해도 145 → 200건. **임계값을 낮추지 않고 색인을 늘리는 유일한 지렛대**이므로
   다음 루프 최우선 후보. 다만 태그를 기계적으로 3개씩 붙이면 이 1점은 다시
   "전 사이트 공통 보일러플레이트"가 되어 상투구 방어선(`BOILERPLATE_ORIGIN_PATTERNS`)이
   막으려던 것과 같은 종류의 구멍이 된다 — 태그는 분류로서 의미가 있을 때만 붙일 것.
2. **배너 문구가 색인 유입을 전제하지 않는다.** 지금은 "얇은 문서 = 검색에서 안 보임"이
   전제라 배너가 내부 탐색자만 봤다. C안 이후 257건은 검색 첫 방문자가 본다.
3. **`description` 상한이 254자다.** 배점 구간 400/250/150은 데이터와 맞지 않는다.
   B안(콘텐츠 보강)을 할 때 목표치를 "400자"로 잡을지 배점을 현실에 맞출지 결정 필요.

## 7. 검증 · 롤백

**적용 순서**
1. `lib/content-depth.ts` (§3-1) → `app/(default)/memes/[key]/page.tsx` (§3-2)
   → 테스트 (§3-5) → `scripts/quality-check.mts` (§3-4). **2번을 빠뜨리면 안 된다(리스크 4).**
2. `pnpm vitest run lib/content-depth.test.ts app/sitemap.test.ts components/adsense-script.test.tsx`
3. `npx tsc --noEmit`
4. `node scripts/quality-check.mts` → `depth.indexable === 402`, `depth.substantial === 145` 확인.
   **두 값이 다 안 나오면 배포하지 않는다** — 402는 색인 확대가 실제로 일어났다는 증거이고,
   145는 광고·배너 기준이 안 움직였다는 증거다.
5. 로컬 프로덕션 빌드로 `/sitemap.xml`의 `<url>` 중 `/memes/` 항목 수 = 402 확인.
6. 배포 후 표본 확인: `/memes/7jwfbdck`(신규 색인) → robots에 `noindex` 없음 + 광고 로더 없음 +
   「정리 중」 배너 있음. `/memes/z4ywt995`(현행 충실) → 색인 O + 광고 O + 배너 없음.

**롤백**: `CONTENT_DEPTH_THRESHOLDS.INDEX_MIN_PROSE_CHARS`를 `250`으로 되돌리고 재배포.
상수 한 개다. 함수 분리(§3-1·3-2)는 되돌릴 필요가 없다 — 값이 같아지면 두 관문이
동일하게 동작해 현행과 완전히 같은 결과가 된다. 사이트맵은 재배포로 재생성된다.
