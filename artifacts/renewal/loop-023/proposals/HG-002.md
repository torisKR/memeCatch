# HG-002 구현안 — 안전 등급에서 `gray`(이미 늦음) 분리 (B안)

- 루프: 023 / 작성일: 2026-08-04
- 상태: **제안서. 코드·DB 미변경.** 이 문서의 diff와 SQL은 전부 초안이며 적용하지 않았다.
- 원 결정: `docs/renewal/DECISIONS.md` §HG-002 — 추천안 **B**(`gray`를 안전 스케일에서
  빼고 유행 상태로 이관, 안전은 3단계)
- 데이터 근거: 프로덕션 PostgREST **읽기 전용** 조회
  (`https://onjipuldngbdptldkpoe.supabase.co/rest/v1/memes`, anon key, GET only)

## 0. 요약 5줄

1. `gray` 168건 중 **167건은 이미 `lifecycle_status`가 `archived`(121) 또는 `cooling`(46)**
   이다. 시의성 신호는 이미 유행 축에 있고, 안전 축의 `gray`는 그 중복 표기였다.
   → B안의 "유행 상태로 이관"은 **lifecycle 쓰기가 거의 필요 없다**(모순 1건만 사람 판단).
2. 진짜 비용은 lifecycle이 아니라 **safety 재판정 168건 + `usage_context`의 `gray` 192건**이다.
   `usage_context`에 `gray`가 든 문서는 168건이 아니라 **192건**(안전등급이 gray가 아닌 44건 포함).
3. Postgres는 enum 값을 DROP할 수 없다. **enum은 그대로 두고** 백필 후 `CHECK` 제약으로
   재유입만 막는 것이 가장 짧은 경로다(타입 재작성 시 `meme_revisions` 스냅샷·RPC·트리거 전부 재검증 필요).
4. **배포 순서가 안전 요건이다.** `SAFETY_LEVELS[meme.safety_level]` 무방비 조회가 6곳 있어
   코드를 먼저 배포하면 잔존 `gray` 행에서 런타임 크래시가 난다. **DB 백필 → 코드 배포** 순서 고정.
5. 재분류는 **보수 기본값 `yellow`(R-B)** 를 권한다. 증거 기반 3분류(R-A)는 91건을 `써도 됨`으로
   올리는데, 그 근거가 `usage_context.friends=green` 단 하나뿐이고 HG-003이 지적한
   "직장·가족 맥락 오안내" 위험 방향과 정확히 겹친다.

### 1.2 핵심 발견 — 시의성 신호는 이미 유행 축에 있다

`gray` 168건의 `lifecycle_status`:

| lifecycle_status | 건수 | 사용자 노출 문구 |

| `archived` | **121** | 추억 밈 |

| `rising` | **1** | 급상승 ← **모순** |

즉 167/168은 "이미 늦음"을 **안전 배지와 생명 게이지 두 곳에서 중복으로** 말하고 있었다.
`gray`를 안전 축에서 빼도 시의성 정보는 하나도 사라지지 않는다. 이것이 B안을
DECISIONS의 비용 추정("높음")보다 싸게 만드는 지점이다.

### 1.3 `usage_context` 안의 `gray` — 168건이 아니라 192건

`usage_context` jsonb의 4개 키(work/friends/family/sns)별 `gray` 개수:

| 키 | green | yellow | **gray** | red |
| --- | ---: | ---: | ---: | ---: |
| work | 3,309 | 318 | **168** | 107 |
| friends | 3,864 | 26 | **4** | 8 |
| family | 3,376 | 237 | **187** | 102 |
| sns | 3,433 | 239 | **134** | 96 |

- `usage_context`에 `gray`가 하나라도 든 문서: **192건**
- 그중 `safety_level <> 'gray'`인 문서: **44건**
  (green 35 / yellow 5 / red 4 — 44건 전부 `lifecycle_status='cooling'`)
- 반대로 `safety_level='gray'`인데 `usage_context`에 `gray`가 없는 문서: **20건**

즉 두 필드는 이미 어긋나 있다. **`safety_level`만 고치면 화면에 `◌ 이미 늦음`이 상황별 표에
그대로 남는다.** `usage_context` 백필 범위는 **192건**, 두 필드를 합친 영향 문서는 **212건**
(교집합 148)이다 — 168이 아니다.

| --- | ---: |

| `green`+`yellow` 혼합 | 11 |

"친구끼리는 통하지만 공적 자리에서는 늦었다"를 안전 값으로 기록해 둔 것이다.

### 1.4 랭킹 영향 — `compute_trend_scores()`의 safety 밴드

`supabase/migrations/20260716030000_preserve_content_updated_at.sql:117-124`:

```sql
trend_score = case
  when s.eligible and m.safety_level = 'green'  then 300 + s.signal_score + s.completeness / 10.0
  when s.eligible and m.safety_level = 'yellow' then 200 + s.signal_score + s.completeness / 10.0
  when s.eligible                               then 100 + s.signal_score + s.completeness / 10.0
  else least(99::double precision, s.completeness / 2.0 + s.signal_score)
end
```

`gray`는 `red`와 같은 100 밴드에 있다. 등급이 바뀌면 밴드가 통째로 이동한다.

현재 밴드 분포:

| 밴드 | 문서 수 |
| --- | ---: |
| ≥300 (green·eligible) | 1,440 |
| 200–300 (yellow·eligible) | 196 |
| 100–200 (gray/red·eligible) | 47 |
| <100 (ineligible) | 2,221 |

`gray` 168건 중 **랭킹 자격(`is_meme_rank_eligible`) 통과 = 25건**(전부 `trend_score` 109.5).
나머지 143건은 `<100` 구간이라 등급을 바꿔도 순위가 움직이지 않는다.

25건 이동 후 예상 순위:

| 규칙 | 새 trend_score | 위에 있는 문서 수 | 실질 순위 |
| --- | ---: | ---: | --- |
| R-A green 판정 시 | 309.5 | 1,440 | 1,441위권 |
| R-B yellow 고정 시 | 209.5 | 1,636 | 1,637위권 |

**둘 다 랭킹 1페이지에 닿지 않는다.** 오늘 top-12는 전부 `green` 334.9~354.5 구간이다.
→ 랭킹 보드 가시 영향 0. 다만 `/rankings` 하위 페이지와 `trend_score` 정렬 API 응답은 바뀐다.

25건의 `usage_context`는 **25건 전부** `{work:gray, family:gray, sns:gray, friends:green}` 이다.
예: `훈수충`, `마빡이`, `따봉`, `뿌잉뿌잉`, `내가 고자라니 (심영물)`,
`콜드플레이 키스캠 밈`, `FIFTY FIFTY 전속계약 분쟁`.

### 1.5 `rising` 자동 승격 규칙과의 충돌 (잠재 위험)

같은 함수 `:139-145`:

```sql
update public.memes set lifecycle_status = 'rising'
where moderation_status in ('approved','limited')
  and trend_score > 300
  and published_at > now() - interval '14 days'
  and lifecycle_status <> 'rising';
```

- `gray` 168건 중 최근 14일 내 `published_at`: **37건**
- 그 37건 중 랭킹 자격 통과: **0건** → 오늘 당장 승격되는 문서는 **0건**

즉 즉시 위험은 없다. 그러나 R-A로 `green` 승격 시 이 문서들이 자격을 갖추는 순간
`archived`(추억 밈) → `rising`(급상승)으로 자동 전이한다. `archived`를 제외하는 조건이
규칙에 없기 때문이다. **R-B(yellow, 200 밴드)를 택하면 `trend_score > 300` 조건에
영구히 걸리지 않아 이 경로가 원천 차단된다.**

## 4. 마이그레이션 SQL 초안 — **적용 금지**

> 이 SQL은 실행하지 않았다. 프로덕션은 이 루프에서 읽기 전용이다.
> 파일명 예시: `supabase/migrations/20260805000000_safety_level_drop_gray.sql`

### 4.1 왜 enum을 재작성하지 않는가

Postgres에는 `ALTER TYPE ... DROP VALUE`가 없다(PG 17 기준). 타입을 갈아끼우려면
rename → 새 타입 생성 → 컬럼 `using` 캐스팅 → 의존 객체 재컴파일 → 구 타입 drop 이 필요한데,
`public.safety_level`에 의존하는 것이 다음과 같다:

- `memes.safety_level` 컬럼 (`20260708004500_schema_v2.sql:89`)
- `compute_trend_scores()` 의 safety 밴드 CASE
- `complete_seo_campaign_item()` 의 `(p_content ->> 'safety_level')::public.safety_level`
  (`20260716040000_seo_campaigns.sql:340`)
- `protect_active_seo_holdout()` 트리거의 튜플 비교 (`:441,445`)
- `meme_revisions.snapshot`(jsonb)에 문자열 `"gray"`로 굳은 과거 스냅샷

**enum 값은 남기고 CHECK 제약으로 재유입만 막는 것**이 가장 짧고 되돌리기 쉽다.

### 4.2 사전 점검 (읽기 — service_role 필요, anon으로는 401)

```sql
-- [PRE-1] 활성 SEO 홀드아웃에 걸린 문서가 있으면 UPDATE가 통째로 실패한다.
--         트리거: protect_active_seo_holdout() → 'active_seo_holdout_is_read_only'
--         (safety_level 또는 usage_context 변경을 감지한다)
select m.id, m.slug, c.id campaign_id, c.state
from public.memes m
join public.seo_campaign_items i on i.meme_id = m.id and i.bucket = 'holdout'
join public.seo_campaigns c on c.id = i.campaign_id
where c.state in ('ready', 'in_progress', 'measurement_due')
  and (m.safety_level = 'gray'
       or m.usage_context::text like '%"gray"%');
-- 0행이어야 진행. 1행이라도 나오면 그 문서를 백필 대상에서 제외하거나 캠페인 종료 후 재시도.

-- [PRE-2] 대상 건수 확정.
--         실측(2026-08-04): safety_gray 168, ctx_gray 192, 교집합 148, 합집합 212.
select count(*) filter (where safety_level = 'gray') as safety_gray,          -- 기대 168
       count(*) filter (where usage_context->>'work'    = 'gray'
                          or usage_context->>'friends' = 'gray'
                          or usage_context->>'family'  = 'gray'
                          or usage_context->>'sns'     = 'gray') as ctx_gray, -- 기대 192

                          or usage_context->>'work'    = 'gray'
                          or usage_context->>'friends' = 'gray'
```

### 4.3 본 마이그레이션 (R-B 규칙 기준)

```sql
-- 20260805000000_safety_level_drop_gray.sql
-- HG-002 / 루프 023. 안전 축에서 시의성 값 'gray'를 분리한다.
-- 시의성은 lifecycle_status(cooling/archived)가 단독으로 말한다.
-- 실측(2026-08-04): safety_level='gray' 168건, lifecycle archived 121 / cooling 46 / rising 1.
-- 재판정 규칙 R-B(보수): 증거가 red를 가리키지 않는 한 전부 yellow(스키마 기본값)로 내린다.
begin;

-- 0) 감사 근거를 먼저 남긴다. 되돌릴 때 이 스냅샷이 유일한 원본이다.
insert into public.meme_revisions (meme_id, editor_id, snapshot, note, status)
select m.id, null, to_jsonb(m), 'HG-002 gray→safety axis split (loop-023)', 'approved'
from public.memes m
where m.safety_level = 'gray'
   or m.usage_context->>'work'    = 'gray'
   or m.usage_context->>'friends' = 'gray'
   or m.usage_context->>'family'  = 'gray'
   or m.usage_context->>'sns'     = 'gray';
-- 기대: 212행 (safety_gray 168 ∪ ctx_gray 192, 교집합 148)

-- 1) 모순 1건은 규칙 백필에서 제외한다 (rising + work=red + safety=gray).
--    slug='밤티' — 사람 검수 후 개별 처리.
create temp table hg002_manual as
select id from public.memes
where safety_level = 'gray' and lifecycle_status = 'rising';
-- 기대: 1행

-- 2) safety_level 재분류 — R-B
--    red: usage_context에 red가 있는 문서만. 그 외 전부 yellow.
--    (green 승격은 자동으로 하지 않는다 — §5 참조)
update public.memes m
set safety_level = 'red', updated_at = now()
where m.safety_level = 'gray'
  and m.id not in (select id from hg002_manual)
  and (m.usage_context->>'work'    = 'red'
    or m.usage_context->>'friends' = 'red'
    or m.usage_context->>'family'  = 'red'
    or m.usage_context->>'sns'     = 'red');
-- 기대: 3행 (rising 1건 제외 후)

update public.memes m
set safety_level = 'yellow', updated_at = now()
where m.safety_level = 'gray'
  and m.id not in (select id from hg002_manual);
-- 기대: 164행

-- 3) usage_context의 'gray' 제거 — 값을 바꾸지 않고 '미확인'으로 비운다.
--    HG-003 C안과 같은 입장: 모르는 것을 green으로 채우지 않는다.
--    파급: is_meme_rank_eligible 는 usage_context <> '{}' 만 요구하므로
--          friends 키 하나만 남아도 자격은 유지된다.
update public.memes m
set usage_context = (
      select coalesce(jsonb_object_agg(k, v), '{}'::jsonb)
      from jsonb_each_text(m.usage_context) as e(k, v)
      where v <> 'gray'
    ),
    updated_at = now()
where m.id not in (select id from hg002_manual)
  and (m.usage_context->>'work'    = 'gray'
    or m.usage_context->>'friends' = 'gray'
    or m.usage_context->>'family'  = 'gray'
    or m.usage_context->>'sns'     = 'gray');
-- 기대: 192행 (rising 1건 '밤티'의 usage_context 에는 gray 가 없어 제외 조건에 걸리지 않는다)

-- 4) 재유입 차단. enum 값은 남기되 쓰기를 막는다(Postgres는 enum 값 DROP 불가).
alter table public.memes
  add constraint memes_safety_level_no_gray
  check (safety_level <> 'gray') not valid;
alter table public.memes validate constraint memes_safety_level_no_gray;

alter table public.memes
  add constraint memes_usage_context_no_gray
  check (
    usage_context->>'work'    is distinct from 'gray' and
    usage_context->>'friends' is distinct from 'gray' and
    usage_context->>'family'  is distinct from 'gray' and
    usage_context->>'sns'     is distinct from 'gray'
  ) not valid;
alter table public.memes validate constraint memes_usage_context_no_gray;

-- 5) 검증 — 하나라도 0이 아니면 롤백한다.
do $$
declare v_left integer;
begin
  select count(*) into v_left from public.memes
  where safety_level = 'gray'
     or usage_context->>'work'    = 'gray'
     or usage_context->>'friends' = 'gray'
     or usage_context->>'family'  = 'gray'
     or usage_context->>'sns'     = 'gray';
  if v_left <> 1 then  -- hg002_manual 1건만 남아야 한다
    raise exception 'HG-002 backfill left % gray rows (expected 1)', v_left;
  end if;
end $$;

commit;
```

> 3단계 이후 `hg002_manual`의 1건은 **CHECK 제약에 걸려 남길 수 없다.**
> 실제 적용 시에는 둘 중 하나를 택한다:
> (a) 마이그레이션 전에 `밤티` 1건을 관리자 콘솔에서 수동 판정한 뒤 제약을 건다 — **권장**
> (b) 제약을 `not valid`로만 두고 validate를 미룬다 — 재유입 차단이 약해진다.

## 5. gray 168건 재분류 규칙 — 두 안 비교

### 규칙 R-A — 증거 기반 3분류

```
1) usage_context 값에 'red' 가 하나라도 있으면        → red
2) 아니고 usage_context 에 'yellow' 가 있거나
   caution 이 비어 있지 않으면                        → yellow
3) 그 외                                              → green
```

실측 결과: **green 91 / yellow 73 / red 4**
(lifecycle 교차: archived-green 78, archived-yellow 43, cooling-yellow 30,
cooling-green 13, cooling-red 3, rising-red 1)

### 규칙 R-B — 보수 기본값 (**추천**)

```
1) usage_context 값에 'red' 가 하나라도 있으면        → red
2) 그 외 전부                                         → yellow  (스키마 기본값)
3) lifecycle_status='rising' 1건은 백필 제외 → 사람 검수
```

실측 결과: **yellow 164 / red 3 / 수동 1**

### R-B를 추천하는 근거

| 항목 | R-A | R-B |
| --- | --- | --- |
| `써도 됨`으로 승격되는 문서 | **91건** | 0건 |
| 승격 근거 | 132건은 `usage_context.friends=green` **단 하나** | — |
| HG-003 위험(직장·가족 오안내)과의 방향 | 위험을 **키운다** | 중립 |
| `archived → rising` 자동 전이 경로 | 열린다 (300 밴드 진입) | 원천 차단 (200 밴드) |
| 사람이 봐야 할 문서 | 0 (전량 기계 판정) | 25건(랭킹 노출분)만 후속 승격 심사 |
| 되돌릴 때 손해 | green→yellow 강등이 사용자에게 보임 | yellow→green 승격은 보상 방향 |

`gray` 168건 중 랭킹에 실제로 노출되는 건 **25건뿐**이다. R-B로 전량 `yellow`에 놓고,
그 25건만 사람이 보고 `green`으로 올리면 1인 운영에서 감당 가능한 작업량이 된다.
DECISIONS가 "운영 비용 높음"으로 본 168건 재판정이 **25건 심사**로 줄어든다.

### `usage_context`의 `gray` 192건 처리 — DQ-H2 실측 비교

| 처리 | 이 192건 중 `uniform` 되는 문서 | DQ-H2 전체 (기준선 3,310 / 84.78%) |
| --- | ---: | --- |
| 현행 | 2 | 3,310 (84.78%) |
| `gray → green` 치환 | **157** | **3,465 (88.8%)** ← +155 악화 |
| **키 제거(미확인)** ← 추천 | **35** | **3,343 (85.6%)** ← +33 |

`gray → green` 치환은 130건짜리 단일 패턴
`{work:gray, family:gray, sns:gray, friends:green}` 을 통째로 전부-green 으로 만들어
HG-003이 지적한 "상황별 표가 데이터 없이 판정처럼 보이는" 문제를 **직접 키운다.**
키 제거 쪽은 `components/usage-guide.tsx:11-28`의 `isSafetyLevel` 필터 덕분에

## 7. 남은 사람 결정 (이 문서가 정하지 않은 것)

1. **`밤티` 1건** (`rising` + `work=red` + `safety=gray`). 규칙으로 정할 수 없다.
2. **R-A vs R-B.** 본 문서는 R-B를 추천하지만, "옛 밈은 대체로 안전하다"는 편집 판단을
   택한다면 R-A(green 91)도 성립한다. 단 §5 표의 위험을 감수하는 결정이다.
3. **25건 승격 심사 시점.** DECISIONS는 HG-003과 묶어 한 번에 처리할 것을 권했다.
   `usage_context` 키 제거(§5)는 HG-003 C안의 `미확인` 표시를 전제로 하므로,
   HG-003 C안 없이 이 백필만 적용하면 상황별 표가 1행짜리로 남는 문서가 191건 생긴다.
4. **`/editorial` 개정 공표.** 편집 원칙 변경이므로 `EFFECTIVE`(현재 "2026년 7월 26일")
   갱신과 변경 이력 표기가 필요하다.
