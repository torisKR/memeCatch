## 5. 검색어 수집 완화 (ANL-002) — 길이 제한 vs 해시

### 5.1 먼저: DECISIONS.md의 범위 파악이 좁다

DECISIONS.md:232는 「`search_submit`·`search_no_result` 2종이 원문을 보낸다」고 적었다. **실제로는 4종이다.**

| 이벤트 | 파일:줄 | 검색어 처리 |
| --- | --- | --- |
| `search_submit` | `components/search-outcome-tracker.tsx:47` | 100자 slice (`MAX_QUERY_LENGTH`, 26줄) |
| `search_no_result` | `components/search-outcome-tracker.tsx:52` | 100자 slice |
| `search_result_click` | `app/(default)/search/page.tsx:61` | **무제한 원문** (`params={{ query }}`) |
| `search_suggest_click` | `app/(default)/search/search-input.tsx:143` | **무제한 원문** (`{ query: trimmed, … }`) |

그리고 **가장 큰 노출은 이벤트가 아니라 URL이다.**
검색어는 `?q=`로 주소창에 들어간다(`search-input.tsx:70` — `router.replace('/search?q=' + encodeURIComponent(trimmed))`).
GA4 기본 `page_view`의 `page_location`에 그 URL이 통째로 실린다.
또한 `q`는 **GA4 향상된 측정 「사이트 검색」의 기본 쿼리 파라미터**라, 원문이 `search_term`으로도 수집될 수 있다.
→ **커스텀 이벤트 4종을 전부 고쳐도 노출은 닫히지 않는다.** GA4 관리화면 설정이 함께 필요하다(§8 미확인 항목).

### 5.2 두 방식 비교

| 기준 | (A) 길이 제한 | (B) 해시 (SHA-256 앞 12자) |
| --- | --- | --- |
| **개인정보 저감** | **거의 없음.** 「홍길동」 3자, 「010-1234-5678」 13자, 이메일 20자 내외 — 전부 어떤 상한도 통과한다. 게다가 **GA4 파라미터 값 상한 자체가 100자**라, 현행 `slice(0,100)`은 GA가 어차피 하는 일과 같다 → **현행 저감 효과 ≈ 0** | 중간. 보고서 화면에서 원문이 사라진다 |
| **분석 가치** | **완전 보존.** 0건 검색어 원문을 읽어 콘텐츠 갭을 발굴하는 것이 `search_no_result`의 존재 이유다 | **거의 소실.** 해시는 사람이 못 읽는다. 「같은 값이 N번 나왔다」는 빈도만 남고 「무엇을 찾다 실패했는가」는 사라진다 — 이벤트를 지우는 것과 실효가 비슷하다 |
| **구현 비용** | `slice` 한 줄 × 4곳. 동기 | `crypto.subtle.digest`는 **비동기 + Secure Context 한정**. `track()` 호출부가 async가 되거나 별도 큐가 필요하다. 동기 비암호 해시(djb2 등)로 낮추면 충돌·역산이 오히려 쉬워진다 |
| **남는 위험** | 원문이 GA4(국외 제3자)에 그대로 적재 | **역산 가능.** 한국어 검색어 공간은 작다 — 밈 이름 사전 + 흔한 성명 조합으로 사전 대조 복원이 가능하다. 솔트를 붙이면 역산은 막히지만 **솔트가 클라이언트 번들에 노출**되어 무의미하다 |
| **PIPA 관점** | 개인정보 그대로 | 솔트 없는 해시는 **가명처리** 수준 — 익명정보가 아니며 여전히 개인정보다. 처리방침 고지·보관기간 의무가 그대로 남는다 |
| **`page_location` 누수** | 해결 못 함 | 해결 못 함 |

**결론: 둘 다 단독으로는 부적합.** (A)는 위험을 줄이지 않고, (B)는 위험을 조금 줄이면서 가치를 전부 없앤다.

### 5.3 권고 — (C) 결과 유무 분기 + PII 패턴 차단

**원리:** 결과가 1건 이상 나온 검색어는 **공개된 밈 데이터와 실제로 매칭된 문자열**이다.
사용자의 이름·연락처가 밈 인덱스에 매칭될 확률은 사실상 0 → 그 검색어는 개인정보 위험이 낮다.
위험은 **결과 0건, 즉 어디에도 매칭되지 않은 자유 입력**에 집중된다. 거기에만 방어를 건다.

```diff
--- a/lib/analytics.ts   (신규 헬퍼 — 4개 호출부가 공유)
+/** GA4로 내보낼 검색어를 다듬는다.
+ *
+ * 왜 길이 제한만으로는 안 되는가: GA4 파라미터 값 상한이 이미 100자다. 100자 slice는
+ * 개인정보를 하나도 걸러내지 못한다 — 이름·전화번호·이메일은 전부 그보다 짧다.
+ * 왜 해시를 쓰지 않는가: 검색어 공간이 작아 사전 대조로 복원되고, 복원되지 않더라도
+ * 「무엇을 찾다 실패했는가」를 못 읽게 되어 이벤트의 목적이 사라진다.
+ *
+ * 상한 30자 근거: 공개 밈 제목 3,904건의 p99 = 28자, 30자 초과는 25건(0.6%).
+ * 즉 알려진 밈 이름의 99.4%는 그대로 통과하고, 그보다 긴 자유 문장만 버킷으로 접힌다.
+ */
+const MAX_SEARCH_TERM = 30;
+const PII_PATTERNS = [
+  /[\w.+-]+@[\w-]+\.[\w.]+/,             // 이메일
+  /\d{2,3}[-.\s]?\d{3,4}[-.\s]?\d{4}/,   // 전화번호
+  /\d{6}[-\s]?[1-4]\d{6}/,               // 주민등록번호
+];
+
+export function sanitizeSearchTerm(raw: string): string {
+  const q = raw.trim();
+  if (!q) return "(empty)";
+  if (PII_PATTERNS.some((pattern) => pattern.test(q))) return "(redacted)";
+  if (q.length > MAX_SEARCH_TERM) return "(long)";
+  return q;
+}
```

**남는 위험을 숨기지 않는다:** 「홍길동」 3자는 이 필터를 통과한다. 패턴 차단은 **정형 식별자**(이메일·전화·주민번호)만 막고, 비정형 개인정보는 못 막는다. 그 이상을 원하면 결과 0건 검색어의 원문 전송 자체를 포기해야 하고, 그러면 콘텐츠 갭 발굴 수단이 사라진다 — 그 교환은 결정권자의 몫이다.

**동시에 반드시 해야 할 것(코드 밖):** GA4 관리화면에서
(1) 향상된 측정 「사이트 검색」의 `q` 수집 여부 확인 → 켜져 있으면 끄거나 파라미터에서 `q` 제외,
(2) `page_location`에서 쿼리스트링 제거 규칙 적용 여부 확인.
**이 두 가지를 하지 않으면 위 코드 변경은 실효가 절반 이하다.**

## 8. 확인하지 못한 것 (추측으로 채우지 않음)

1. **GA4 관리화면 설정** — 향상된 측정의 사이트 검색 on/off, `page_location` 쿼리 제거 규칙, 데이터 보관기간, 맞춤 측정기준 슬롯 잔여 수. 코드·DB에서 확인 불가. §5의 실효는 여기에 달려 있다.
